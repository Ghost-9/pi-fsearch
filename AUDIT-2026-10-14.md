## 0. TL;DR verdict

The extension's **core engine works and is genuinely fast** — measured p50 **0.03–0.5 ms** for warm socket queries,
**45×–78×** faster than `find`/`rg` on the same scope, with working typo-intolerance, DLP scrubbing, git filters, and a
resident daemon that survives restarts. That part is real.

The **surrounding claims, delivery bookkeeping and observability are not trustworthy**:

| Area | Finding |
|---|---|
| CI | **18 of 18 GitHub Actions runs have failed. Zero passes.** The "CI Gate p95 < 10 ms" badge is false and the benchmark gate has never executed in CI. |
| Test suite | Local 25/25 pass only because a daemon is running. In CI it is 23/25 (`UltraSearchClient ping`, `compactor`). Tests are integration tests, not hermetic. |
| Telemetry | **101 of 139 rows (73%) in the "production" audit log are synthetic rows written by the regression gate.** Real agent calls are mixed with benchmark runs; search/multi-grep calls are recorded twice (inner client + outer tool). |
| Token savings | The TUI's "tokens saved" number is a **hard-coded heuristic** (`150 + 75 × hitCount`), never measured, and double-counted on duplicate rows. |
| Real-world latency | Warm micro-benchmarks are real, but **real agent-session rows show `ultrasearch_query` p50 41 ms, p95 ~1.95 s, max 4.0 s** and **29% native-fallback rate**. |
| Dead code | `semantic.ts`, the Code Mode declaration module, `startAutoCompaction()`, `recordMistake()/learnCorrection()` and `loadIgnoreRules()` are **never invoked by production paths**. |
| Milestones | 15/15 issues closed and "Done" on the project board; at least **#12 is dead code, #14 was never registered anywhere, and #15 is factually wrong** (gate tests a ~25-file repo, not "1M+ file trees"; CI never passed). |
| Versions | `package.json` 0.3.0, README badge 0.2.2, CHANGELOG ends at 0.2.2, **zero git tags, zero GitHub releases**, 14 commits after the last changelog entry. |
| Footprint | Claimed "~21 MB idle RSS" → measured **135 MB now, 391 MB during indexing**; index 121.5 MB + content 134 MB on disk. |

## 4. Telemetry integrity (the "observability" system is not trustworthy yet)

1. **Synthetic contamination:** `test/benchmark-gate.test.ts` does not set `PI_ULTRASEARCH_TEST=1`; every `npm run test:gate`
   writes 100 rows into the production `audit.jsonl`. Confirmed: 101 of 139 rows are `package.json`/`UltraSearchClient` gate rows.
2. **Double recording:** `UltraSearchClient.search()/grep()/multiGrep()` record audit rows *and* the Pi tool wrapper records again.
   Four real calls show exact duplicate pairs (e.g. `*taste*` 39.7/40.8 ms; multi-grep 20.2/47.0 ms with 13 vs 6 hits).
   This inflates call counts, "tokens saved" and distorts percentiles.
3. **Heuristic tokens:** `estimateTokensSaved()` is a formula, not a measurement; it counts *files*, not matched text, and is
   added twice for duplicated calls.
4. **`ultrasearch_compact` rows report the entire index as `hitCount`** (2.9 M) — meaningless in the TUI log.
5. **Recursive learning is a facade:** nothing in production calls `recordMistake()/learnCorrection()`; the TUI displays
   patterns that came from the test suite.

## 6. Security review notes

* Secret scrubbing covers the main families and is unit-tested; DLP masking of `.env`/key files works.
* **Malformed private-key regex** in `src/sanitize.ts` (`[[\s\S]*?`) — multi-line PEM bodies will not match as intended.
* Path containment (`isPathSafe`) is only enforced for `ultrasearch_grep(path_filter)`; `ultrasearch_query` accepts scope/SDK paths
  without a containment check; `global: true` bypasses all scoping by design.
* `scrubSecrets` is applied to grep matches, **not** to `ultrasearch_query` path output (paths can leak usernames/project names; lower risk).
* Nothing in this audit found vault/secret exfiltration paths — reads stay on loopback through the daemon socket.
